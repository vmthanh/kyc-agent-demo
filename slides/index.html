Reviewing these takes staff time · a plain AI chatbot can get them dangerously wrong
KYC means checking that a new customer is who they say they are and is allowed to open an account. These "exceptions" are the cases a machine could not settle alone. They are slow for people and risky for a chatbot, because a wrong "approve" on a sanctions match is a serious compliance failure.

System
If the AI and the rules disagree, the rules win — and the disagreement is recorded
Technical mapping, if asked: four data lookups run in parallel (LangGraph), the model is called through OpenRouter, reconcile_guard applies the executable rules, an interrupt waits for approval, and the action gateway uses an idempotency key so a retry never creates a second ticket. The model cannot call tools or write.

The first rule that matches wins. Each rule has a version and a source, e.g. R-ID-EXP-01@1.0 ← KYC-IDENTITY-12.
Rules live in a file anyone can read · not hidden inside the AI's prompt
In Aitomatic's terms this is the "cognitive ontology": expert judgment as executable, versioned rules. The file is loaded and validated; there is no eval and no free text input. Changing a number in the file changes the decision without editing code. Hard stops like rule 1 are always checked first.

Called "maker-checker". The number and roles of approvers depend on how risky the action is. A reviewer sees the full request (case, action, rule and policy versions), not just a button. This is the "Reflect" step: reviewer feedback → candidate rule → replay on 60 labelled + 5 demo cases → two roles approve → promoted version with an audit log. Any safety regression blocks promotion. State is stored locally for the demo; reset to the shipped rules before presenting.
