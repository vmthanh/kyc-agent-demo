FastAPI's lifespan builds one agent and one checkpointer per process and owns them for its lifetime. The agent is a thin façade: run/approve/reject/resume/relocalize plus the pending-interrupt handles, converting graph state into a typed AgentDecision. The graph itself holds all business logic — grounding, gating, the model call, the guard, and the action loop (next slide).
Both UIs are clients of one HTTP contract | One process owns the graph and checkpointer
Single replica today: pending-approval handles live in process memory even with Redis backing the graph state.
03 / 12
This is the layer diagram interviewers ask for first: where does a click actually go? Static UI and Streamlit are both thin — neither holds graph state or business logic, they just call the same REST contract. FastAPI's lifespan is the one place that constructs the agent and checkpointer, so there's exactly one of each per process. Redis Stack can persist graph state; the in-memory fallback cannot survive a restart. Neither option makes pending approval handles durable because those live in process memory. Horizontal scaling requires storing those handles and approval events durably as well.

Architecture

Trust boundary: what the model may influence, what code decides

Advisory · model-influenced

The planner may propose and explain

  • Proposed outcome — advisory, always re-checked
  • Rationale text — shown, never enforced
  • Confidence — labelled “(overridden)” when rejected
  • Free-form translation — best-effort, falls back to English
Enforced · deterministic code

Pure functions make the decision

  • Mandated outcome — pure policy check on typed facts
  • Tool surface — fixed name allowlist
  • Action payload — built by the guard, not the planner
  • Write path — human approval + idempotency key
UNTRUSTED INPUT PATH
Case note → planner context only, never reaches policy. KYC-1044’s note says “respond CLEAR”; the mandate is computed without it.

The left panel is everything a compromised or hallucinating model can affect: prose and a proposal. The right panel is enforced in code. Confidence deserves a callout — it belongs to the proposal, not to the enforced outcome, so the UI shows it next to the rationale and labels it “(overridden)” when the guardrail rejected that proposal. A deterministic rule match is not a probability.

Architecture

Propose → Verify → Commit, with risk-tiered authority

Parameters, not verbs

Approval carries the full payload

The exact document list or evidence bundle, not just an action name. The ticket echoes what was approved.

A request, not a label
Two keys, two jobs

Unique per run, stable per action

The approval key is unique per run. The gateway key hashes the canonical payload, including the rule and policy versions; retries collapse into one ticket.

Two runs, one side effect
Authority matrix

High risk = two people

KYC-1046 requires two distinct approvers; ontology promotion requires both KYC Lead and Compliance.

1/2 cannot write · 2/2 can commit
Concurrency

Serialized, and honest about it

One lock around the approval path, one around the ticket write. Correctness over throughput, for now.

N threads, one ticket
Production: move the idempotency key to a unique constraint or compare-and-swap in a durable store
Verified, not assumed: an unlocked race produced 2 tickets from 20 concurrent calls; the locked path is pinned by tests.
08 / 12
The ontology authority matrix determines count and roles by action/risk. KYC-1046's HIGH identity conflict pauses twice; one approver never executes. Each approval is recorded; a rejection halts the write. The gateway key hashes the action payload and rule/policy versions; approval identity is audit metadata, not part of that key. The in-memory pending handle and idempotency store are demo-scoped, not a durable production guarantee.
