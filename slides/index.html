KYC means checking that a new customer is who they say they are and is allowed to open an account. These "exceptions" are the cases a machine could not settle alone. They are slow for people and risky for a chatbot, because a wrong "approve" on a sanctions match is a serious compliance failure.

What one checkpoint holds
  • Facts from the 4 checks + policy citations
  • AI proposal and the rule decision
  • Answers already given at a pausee.g. approval 1 of 2, replayed in order on resume
  • Trace and tool callsappend-only lists: they only grow
This is workflow memory, not chat memory · every run starts on a fresh thread; the AI never “remembers” past cases
The graph is compiled with a checkpointer. LangGraph writes a checkpoint of WorkflowState after each super-step, keyed by thread_id. interrupt() stops the run and returns the pending task to the API; approve/reject/resume call graph.invoke(Command(resume=...)) with the same config, so LangGraph reloads the last checkpoint and re-runs action_review from its start: earlier interrupt() calls get their saved answers back in order, and the new answer goes to the next interrupt(). That is how the two-person approval rebuilds "1 of 2" deterministically. Consequence: code before interrupt() must be side-effect free, which is why the write happens in execute_action. trace, tool_calls and tool_errors use an operator.add reducer, so they only ever grow. A new uuid per run means no state leaks between cases or into the model's prompt.

Redis makes the workflow durable · the approval handles are not yet, so this runs as one server today
Be precise when asked "is it durable?": the graph state is, with Redis; the handle the API uses to find a paused run (graph object + config) is in process memory, and so is the idempotency log. After a restart Redis still has the checkpoint, but the API no longer knows the approval key. Fix: persist pending tasks (interrupt id → thread_id, case, required approvals) and the idempotency log in a database, then any replica can resume any thread. A broken REDIS_URL degrades loudly instead of failing silently; credentials are never logged.

// data/ontology.json · rule 1
{ "id": "R-AML-01", "version": "1.0",
  "priority": 10, "hard_stop": true,
  "params": { "threshold": 0.8 },
  "when": { "all": [{
    "fact": "screen_sanctions.match_score",
    "op": ">=", "value": "@threshold" }] },
  "then": { "outcome": "ESCALATE_COMPLIANCE",
            "action": null },
  "source": { "kind": "policy",
              "ref": "AML-SCREEN-02 §2.3" } }
Loaded by app/ontology.py: schema-validated, closed operator set (>= < is_true empty …), no eval, hard stops must come first, case_note rejected as input.
Rules live in a file anyone can read · not hidden inside the AI's prompt
In Aitomatic's terms this is the "cognitive ontology": expert judgment as executable, versioned rules. The file is loaded and validated; there is no eval and no free text input. Changing a number in the file changes the decision without editing code. Hard stops like rule 1 are always checked first.

Under the hood · app/names.py → R-ID-EXP-01@1.0
Strip accents, then map OCR look-alikes (l→i, rn→m, 0→o) → fact name_diff.ocr_explainable. Rule fires only if ocr_explainable ∧ liveness_passed ∧ tamper_score < 0.10 ∧ nothing missing. Otherwise R-ID-01 → manual review.
The expert's tip helps with blur · it can never approve a customer by itself
The tip "Vietnamese accents are often lost by the scanner" is written as rule R-ID-EXP-01. It never approves an account; it only asks for a better photo. The new photo is checked again and passes on the second round. The expert source is demo metadata, not a real bank's sign-off.

Under the hood · app/reflect.py
Reject → signal → POST /api/amendments → candidate validated by the ontology loader → replay 60 labelled + 5 demo cases → any safety regression blocks → promote_amendment needs kyc_lead + compliance (distinct roles) → new version in .runtime/ontology/ + append-only audit log.
Feedback makes the rules better · the safety re-test stops it making them worse
This is the "Reflect" step: reviewer feedback → candidate rule → replay on 60 labelled + 5 demo cases → two roles approve → promoted version with an audit log. Any safety regression blocks promotion. State is stored locally for the demo; reset to the shipped rules before presenting.
