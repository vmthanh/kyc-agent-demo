FastAPI's lifespan builds one agent and one checkpointer per process and owns them for its lifetime. The agent is a thin façade: run/approve/reject/resume/relocalize plus the pending-interrupt handles, converting graph state into a typed AgentDecision. The graph itself holds all business logic — grounding, gating, the model call, the guard, and the action loop (next slide).
Both UIs are clients of one HTTP contract | One process owns the graph and checkpointer
Single replica today: pending-approval handles live in process memory even with Redis backing the graph state.
03 / 12
This is the layer diagram interviewers ask for first: where does a click actually go? Static UI and Streamlit are both thin — neither holds graph state or business logic, they just call the same REST contract. FastAPI's lifespan is the one place that constructs the agent and checkpointer, so there's exactly one of each per process. The checkpointer (Redis Stack or in-memory fallback) makes graph state durable across a restart; it does not by itself make the service horizontally scalable, because pending-approval handles are still process-local — that's the explicit, named scale boundary, not a hidden gap.

Architecture

The graph itself was upgraded: from a linear chain to a risk-adaptive workflow

Before · linear chain

One path, one shot

  • Grounding — 4 reads run one at a time
  • Failures — one tool error fails the run
  • Model gating — reasons against whatever facts exist
  • Routing — approve-or-block only
  • Resume — one bolted-on interrupt path
  • Code shape — one ~600-line class
After · risk-adaptive graph

Parallel, retried, resumable

  • Grounding — 4 reads run in parallel, fan in at one gate
  • Failures — retry with backoff, then a safe-failure route
  • Model gating — evidence + policy checked before the model sees the case
  • Routing — guard routes to 4 named outcomes, plus a resume cycle
  • Resume — run/resume/approve/reject on native interrupt ids
  • Code shape — 4 small modules, each independently tested
Same safety boundary, now resilient to failures and able to loop a case through more than one evidence cycle
05 / 12
This is the upgrade slide, not the steady-state architecture slide before it. The legacy agent.py was one KYCExceptionAgent class with a five-node chain and a single approval interrupt; document resubmission was a special case bolted on rather than a graph cycle. The rewrite makes grounding parallel, adds retry policies per node class, splits gating (evidence_gate, policy_precheck) ahead of the model call, and generalizes the interrupt contract so approval, document submission and operational review all resume the same way. Net result: faster grounding, safer under transient failures, and cases can cycle through more than one round of evidence without new code — at the cost of more files, which is why each one is independently tested.
Architecture

Trust boundary: what the model may influence, what code decides

Advisory · model-influenced

The planner may propose and explain

  • Proposed outcome — advisory, always re-checked
  • Rationale text — shown, never enforced
  • Confidence — labelled “(overridden)” when rejected
  • Free-form translation — best-effort, falls back to English
Enforced · deterministic code

Pure functions make the decision

  • Mandated outcome — pure policy check on typed facts
  • Tool surface — fixed name allowlist
  • Action payload — built by the guard, not the planner
  • Write path — human approval + idempotency key

The left panel is everything a compromised or hallucinating model can affect: prose and a proposal. The right panel is enforced in code. 07 / 12
Branch order matters and is exhaustive: a screening hit always wins, then identity integrity, then evidence completeness, then the no-exception case. The module is pure and cheap to unit test, which is why the policy branches have full coverage. Verdicts carry reason_key plus params rather than a sentence, so English and Vietnamese render from the same verdict at the presentation boundary.
Architecture

The action boundary: approve parameters, execute once

Parameters, not verbs

Approval carries the full payload

The exact document list or evidence bundle, not just an action name. The ticket echoes what was approved.

A request, not a label
Two keys, two jobs

Unique per run, stable per action

The approval key is unique per run. The gateway key is a hash of case + action, so retries collapse into one ticket.

Two runs, one side effect
Read / write split

Reads inline, writes gated

Reads run automatically. Writes pause for approval; CLEAR and ESCALATE_COMPLIANCE have nothing to approve.

No unapproved side effects
Concurrency

Serialized, and honest about it

One lock around the approval path, one around the ticket write. Correctness over throughput, for now.

N threads, one ticket
Production: move the idempotency key to a unique constraint or compare-and-swap in a durable store
Verified, not assumed: an unlocked race produced 2 tickets from 20 concurrent calls; the locked path is pinned by tests.
08 / 12
The two-key design is the detail worth dwelling on. A reviewer’s approval handle must be unique per run or approving one run could resume another; the gateway’s dedup key hashes the canonical payload and policy versions so retries replay one ticket while changed requests get a distinct key. Different lifetimes, different keys. And I am explicit that an in-process lock is a demo-scoped answer.

Tell the concrete debugging story rather than the abstract loop. An early design could combine untrusted note text with a notification action; the fix was structural — read/write separation and a stop rule outside the model — and then it became a permanent eval. A taxonomy beats a raw test count: each layer has a detection signal and a defined response. CI uses deterministic eval doubles; a separate opt-in smoke command checks the live provider path.
