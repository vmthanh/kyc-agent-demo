Problem

A KYC exception is a policy-bound workflow, not a question to answer

An analyst must reconcile customer data, document evidence, sanctions screening, risk tier and a changing policy book before acting.
Nothing in that loop is a lookup. Each exception is a decision with a mandated outcome, an evidence trail, and a named human accountable for it — and the systems that hold the facts do not hold the policy.
01

Fragmented evidence

Case system, document verification, screening and risk scoring are four separate authorities.

02

Policy that moves

Rules are versioned and jurisdictional; the rationale must cite the version in force.

03

Asymmetric cost of error

Wrongly clearing a screening hit is a compliance incident; wrongly blocking loses a customer.

Today’s chain: read case → verify documents → screen sanctions → pull risk tier → find policy → decide → write ticket
03 / 20
Frame this as a workflow problem. Seven steps, four authoritative systems, one irreversible decision at the end. The analyst’s scarce resource is not knowledge, it is the reconciliation work and the accountability. That is what an agent can carry — and exactly why it must not be free to act.

Why not today

Each existing approach misses a different requirement

Manual queue

Analysts reconcile everything by hand

Correct and accountable, but slow, inconsistent between reviewers, and impossible to scale with onboarding volume. Rationale quality depends on who picked up the case.

Breaks on: throughput and consistency
Rules / RPA

Hard-coded scripts over fixed screens

Deterministic and auditable, but brittle: every new document type, policy version or exception shape is a code change. Cannot read evidence, cannot explain itself.

Breaks on: change and ambiguity
Chatbot + RAG

Retrieves policy text and summarizes

Strong at grounding a paragraph, wrong shape for the work: no state across steps, no tool contracts, no approval gate — and it will paraphrase policy it never verified.

Breaks on: state, tools and safe action
A wrong autonomous action here is a compliance incident, so “usually right” is not a bar this workflow accepts

Why an agent

The model proposes; a deterministic guardrail decides

The design question is not “how good is the model?” — it is “what happens when the model is wrong, hallucinating, or manipulated?”
So the model’s output is advisory. Domain meaning lives in an ontology, facts come from allowlisted tools, the mandated outcome is recomputed in pure code, and every write waits for a named human.
01

Customer, application, evidence, risk finding, policy, resolution, approval — plus constraints.

02

Grounded tools

Authoritative reads with schema-validated outputs, attributed to their source and timed.

03

Bounded action

Deterministic mandatory stops, human approval for writes, idempotent execution.

Architecture

Trust boundary: what the model may influence, what code decides

Advisory · model-influenced

The planner may propose and explain

  • Proposed outcome — advisory only, always re-checked
  • Rationale text — shown to the reviewer, never enforced
  • Self-reported confidence — labelled “(overridden)” when rejected
  • Free-form translation — best-effort, falls back to English
Enforced · deterministic code

Pure functions make the decision

  • Mandated outcome — policy.evaluate() over typed facts
  • Tool surface — DomainTools.call name allowlist
  • Action payload — built by guard(), not by the planner
  • Write path — human approval + idempotency key
UNTRUSTED INPUT PATH

Branch order matters and is exhaustive: a screening hit always wins, then identity integrity, then evidence completeness, then the no-exception case. The module is pure and cheap to unit test, which is why the policy branches have full coverage. Verdicts carry reason_key plus params rather than a sentence, so English and Vietnamese render from the same verdict at the presentation boundary.
Architecture

The action boundary: approve parameters, execute once

Parameters, not verbs

Approval carries the full payload

The interrupt and the gateway both carry case_id, action, and action-specific fields — the exact document list or evidence bundle. The ticket echoes what was approved.

A request, not a label
Two keys, two jobs

Unique per run, stable per action

approval_key is LangGraph’s interrupt id, unique per run, so two runs never collide. The gateway dedups on sha256(case_id:action), stable, so approving either run yields one ticket.

Two runs, one side effect
Read / write split

Reads inline, writes gated

Read-only tools run automatically in the graph. Writes pause on interrupt() and execute only after approval; CLEAR and ESCALATE_COMPLIANCE skip through with nothing to approve.

No unapproved side effects
Concurrency

Serialized, and honest about it

One coarse RLock around run/approve/relocalize, plus a lock on the check-through-insert in execute_approved_action. Correctness over throughput — an explicit port item.

N threads, one ticket
Production: make the idempotency key a unique constraint or compare-and-swap in the durable store — an in-process lock protects one replica only
Verified, not assumed: a throwaway script reproduced the unlocked race (2 tickets from 20 concurrent calls); the locked path is pinned by two concurrency tests that assert every thread’s completion and ticket id, plus a 15-request live curl run.
11 / 20
The two-key design is the detail worth dwelling on. A reviewer’s approval handle must be unique per run or approving one run could resume another; the gateway’s dedup key must be stable per case+action or retries mint duplicate tickets. Different lifetimes, different keys. And I am explicit that an in-process lock is a demo-scoped answer.
