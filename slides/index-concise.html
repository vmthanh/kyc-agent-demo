The problem

A KYC exception requires a decision that is correct, explainable, and safe to act on

Fragmented evidence

Facts live in separate systems

Case data, document checks, sanctions screening, risk tier, and policy evidence must be reconciled for each exception.

Policy changes

The rationale must name the policy in force

Outcomes depend on versioned policy—not a generic summary or a reviewer’s memory.

High cost of error

A wrong action is worse than a slow answer

Clearing a sanctions hit creates a compliance incident; blocking a valid customer creates unnecessary friction.

The job: assemble authoritative evidence, apply the mandated policy, and stop where automation is not permitted.

Trust boundary

The model influences prose and a proposal; code enforces the controls

Advisory · model-influenced

What can vary

  • Recommendation — always checked again
  • Rationale — helps the reviewer understand the case
  • Confidence — attached to the proposal, not the final verdict
  • Free-text translation — best effort, with an honest fallback
Enforced · deterministic

What cannot be bypassed

  • Mandated outcome — pure policy evaluation over typed facts
  • Tool access — named allowlist and structured results
  • Action payload — constructed outside the planner
  • Side effect — human approval and an idempotency key
Untrusted case notes are only planner context. They never enter policy.py, which computes the mandatory outcome.
08 / 15
This is the core system boundary. Policy has no I/O, no model dependency, and no language rendering. The model cannot call the action gateway or manufacture the action payload.

Writes pause in the graph

Read tools run automatically. A write uses LangGraph’s interrupt/resume flow and does not execute without approval.

Idempotency

A stable case + action key deduplicates writes

Repeated approval or retry returns the same ticket instead of creating another operational task.

Retries are safe by construction
Demo scope is explicit: the in-process lock protects one replica; production moves this guarantee to a durable unique constraint or compare-and-swap.

Two distinct keys matter: a per-run approval handle prevents ambiguous resumes; a stable case-plus-action idempotency key prevents duplicate tickets. The deck calls out that a durable store is required for multi-replica production.

Avoid dismissing retrieval. It is necessary for policy evidence, but it cannot by itself manage approvals, side effects, policy enforcement, or a replayable decision trajectory.
Evidence and evaluation

Every layer has a detection signal and a defined response

Data and retrieval

Track freshness, citation quality, and unsupported claims. Retry, filter, or abstain when evidence is weak.

Planning and injection

Replay trajectories and injection cases. The policy guardrail overrides unsafe proposals.

Policy and tools

Use branch coverage and contract validation. Block unresolved policy gaps; retry within a budget.

Actions

Check idempotency and approval events. Return the prior result instead of duplicating a ticket.

Regression loop

Replay → localize → measure → regress

A failure becomes a golden or injection scenario before the next change ships.

Takeaway
A useful KYC agent is not trusted to decide on its own.
It grounds facts, cites policy, proposes a resolution, lets deterministic controls enforce the mandate, and asks a human before any bounded write.
