Trust boundary

The model influences prose; code enforces the controls

Advisory · model-influenced

What can vary

  • Recommendation — always re-checked
  • Rationale — helps the reviewer, not enforced
  • Confidence — on the proposal, not the verdict
  • Translation — best effort, honest fallback
Enforced · deterministic

What cannot be bypassed

  • Mandated outcome — pure policy over typed facts
  • Tool access — fixed allowlist
  • Action payload — built outside the planner
  • Side effect — human approval + idempotency key
Case notes are planner context only. They never reach policy.py, which computes the mandatory outcome.
04 / 9
This is the core system boundary. Policy has no I/O, no model dependency, and no language rendering. The model cannot call the action gateway or manufacture the action payload.

Idempotency

A payload key deduplicates writes

A retry with the same payload replays one ticket. Reusing a resolved approval is rejected; a changed payload gets a new key.

Retry the payload, not the approval
Demo scope: an in-process lock protects one replica; production moves this to a durable unique constraint.
05 / 9
Two distinct keys matter: a per-run approval handle can be used once and a resolved handle raises; the gateway key hashes the canonical payload, including policy versions, so identical gateway retries replay one ticket while materially changed requests remain distinct.

Takeaway
A useful KYC agent is not trusted to decide on its own.
It grounds facts, cites policy, proposes a resolution, lets deterministic controls enforce the mandate, and asks a human before any bounded write.
